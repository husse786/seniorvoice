Performance-Tuning-Session für den lokalen LLM-Betrieb auf dem Raspberry Pi 5. Phase 0: Benchmark-Infrastruktur (SQLite-Logging) schaffen. Phase 1: Hardware-Tuning (CPU Governor) und Modell-Varianten vorbereiten. Phase 2: Benchmarks durchführen und auswerten.

## 2 · Durchgeführte Aktivitäten

### Phase 0 — Benchmark-Infrastruktur (SQLite-Logging)

- **Neuer Env-Var `DB_PATH` in `config.py`** hinzugefügt
  - Default: gleiche SQLite-DB wie `MEMORY_DB_PATH` (`~/seniorvoice/seniorvoice.db`)
  - Separater Env-Var ermöglicht eigenständige DB für Benchmarks falls gewünscht
- **SQLite-Tabellen in `benchmark_models.py`** erstellt (best-effort, crasht Benchmark nie):
  - `benchmark_results` — eine Zeile pro individuellem Run (Prompt × Runde)
  - `benchmark_aggregates` — eine Zeile pro Modell pro Benchmark-Session
- **Schema-Felder:** `run_id` (UUID pro Session), `model`, `model_variant` (Text: stock/tuned/quantized/...), `prompt`, `prompt_number`, `round_number`, `tokens_per_second`, `ttft_ms`, `total_ms`, `token_count`, `response_text`, `is_cold_start`, `error`, `api_base`, `num_rounds`, `timeout`
- **Neue CLI-Flags:**
  - `--no-db` — SQLite-Logging überspringen
  - `--variant` — Model-Variant-Tag (Default: `stock`), z.B. `--variant tuned`
- **Benchmark-Header** erweitert: zeigt DB-Pfad, Variant und Run-ID an
- **Bestehende JSON-Export-Funktion (`--json`)** unverändert — rein additive Änderung
- **Pattern aus `interaction_log.py` übernommen:** WAL-Mode, `_get_db_connection()`, try/finally/close
- **Deployed + getestet auf Pi:**
  - Stock-Run (`gemma3:1b --rounds 1`) — 4 Results + 1 Aggregate in DB
  - Tuned-Run (`gemma3:1b-tuned --rounds 1 --variant tuned`) — korrekt getaggt
  - Vergleichs-Run (`gemma3:1b gemma3:1b-tuned --rounds 3`) — 24 Results + 2 Aggregates
  - `--no-db` Run — keine DB-Einträge, Header zeigt "disabled"
  - DB-Inhalt mit `sqlite3` CLI verifiziert (36 Results, 5 Aggregates)
- **`sqlite3` CLI-Tool auf Pi installiert** (`sudo apt install sqlite3`)

### Phase 1 — CPU Governor, Modell-Varianten & LFM2.5 Import

- **CPU Governor auf `performance` gesetzt (Phase 1A)**
  - Vorher: `ondemand` Governor, Frequenz bei 2.4 GHz (Pi 5 Maximum)
  - `echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor` auf allen 4 Cores
  - Temperatur nach Umstellung: 58.2°C (aktive Kühlung, unkritisch)
  - Persistenz via systemd-Unit `/etc/systemd/system/cpu-performance.service` (Type=oneshot, RemainAfterExit=yes)
  - Service enabled — wird bei jedem Boot automatisch ausgeführt
  - Revert: `sudo systemctl disable cpu-performance.service` + Reboot

- **gemma3:1b-tuned Ollama-Modell erstellt (Phase 1B)**
  - Modelfile: `FROM gemma3:1b`, `PARAMETER num_ctx 512`, `PARAMETER num_batch 128`
  - `ollama create gemma3:1b-tuned` — 815 MB (identisch zu stock, gleiche Weights)
  - `ollama show` bestätigt: `num_ctx 512`, `num_batch 128` aktiv
  - Sanity-Test bestanden: Modell antwortet auf Deutsch

- **LiquidAI LFM2.5-350M importiert (Phase 1C)**
  - `ollama pull liquidai/lfm2.5-350m` — 379 MB (Q8_0, 354M Parameter)
  - LFM2 (Liquid Foundation Model) Architektur, 128k max Context-Length
  - Deutsche Antwortqualität: Kohärent, korrekte Grammatik, relevanter Inhalt
  - Schwäche: Instruction-Following locker (gibt 4 Sätze statt angefragte 2)
  - Getunte Variante `lfm2.5:350m-tuned` erstellt mit `num_ctx 512`

### Phase 2 — Benchmark-Suite: Modellvergleich & Thread-Optimierung

- **Benchmark-Konfiguration:** 4 Prompts × 3 Runden = 12 Runs pro Modell, `--detailed` für Per-Round-Metriken, alle Ergebnisse in SQLite + JSON-Export
- **Temperatur während Benchmarks:** 57.1°C → 60.9°C (unkritisch, aktive Kühlung)

#### Phase 2A — Modellvergleich (alle mit 4 Threads, Default)

| Modell | num_ctx | tok/s (warm) | TTFT warm | TTFT cold | Deutsche Qualität |
|---|---|---|---|---|---|
| gemma3:1b (stock) | 4096 | 4.7 | 1073ms | 4938ms | Gut — korrekte Grammatik, passende Antworten |
| gemma3:1b-tuned | 512 | 4.6 | 1114ms | 4754ms | Gut — gleichwertig zu stock |
| liquidai/lfm2.5-350m | 4096 | 4.6 | 1178ms | 1524ms | Schlecht — inkohärente Witze, grammatische Fehler |

- **Erkenntnis 1:** `num_ctx 512` bringt keinen messbaren Throughput-Gewinn gegenüber Default (4096) bei gemma3:1b
- **Erkenntnis 2:** LFM2.5-350M hat zwar den schnellsten Cold-Start (1524ms vs ~4800ms), aber die deutsche Sprachqualität ist für SeniorVoice unbrauchbar (inkohärente Antworten, z.B. "Ein Kurzhändler kaufte ein Brot vom Markt")
- **Erkenntnis 3:** Performance Governor allein brachte +24% (3.8 → 4.7 tok/s) gegenüber dem alten `ondemand`-Baseline vom 02.05

#### Phase 2B — Thread-Optimierung (gemma3:1b)

Temporäre Ollama-Modellvarianten mit `PARAMETER num_thread N` via Modelfile erstellt und getestet:

| Threads | tok/s (warm) | TTFT warm | TTFT cold | vs. Baseline 3.8 |
|---|---|---|---|---|
| 3 | **8.3** | **914ms** | 4869ms | **+118%** |
| 2 | 7.0 | 1003ms | 5984ms | +84% |
| 4 (Default) | 4.8 | 1183ms | 4739ms | +26% |

- **Erkenntnis 4 (Durchbruch):** `num_thread=3` verdoppelt den Throughput gegenüber Default (4 Threads). Ursache: Bei 4 Threads auf 4 Cortex-A76 Cores bleibt kein Core für Ollama-Server, OS-Scheduling und Memory-Controller frei — Thread-Contention bremst massiv.
- **Erkenntnis 5:** `num_thread=2` ist ebenfalls deutlich besser als 4, aber 3 Threads ist der Sweet Spot.

#### Phase 2C — Produktionsmodell

- **`gemma3:1b-prod` erstellt** mit optimaler Konfiguration:
  - `FROM gemma3:1b`, `PARAMETER num_thread 3`, `PARAMETER num_ctx 512`, `PARAMETER num_batch 128`
  - Benchmark: **8.1 tok/s**, 915ms TTFT (warm), 4811ms TTFT (cold)
  - Innerhalb der Varianz zum reinen 3-Thread-Test (8.3 tok/s)
- **Temporäre Test-Modelle** (`gemma3:1b-t2`, `gemma3:1b-t3`) nach Benchmark gelöscht
- **Alle JSON-Exporte gespeichert** unter `/home/admin/seniorvoice/docs/models/`:

  - `benchmark_tuned_20260503.json`
  - `benchmark_lfm_20260503.json`

## 3 · Technische Entscheide

| Entscheid | Begründung | Verknüpfung RAID |
|---|---|---|
| `DB_PATH` als separater Env-Var (nicht `MEMORY_DB_PATH` wiederverwenden) | Ermöglicht separate Benchmark-DB falls gewünscht; Default zeigt auf gleiche DB | D-30 |
| `model_variant` als Text-Feld statt Boolean `is_tuned` | Flexibler für zukünftige Varianten (stock, tuned, tuned-v2, quantized) | D-31 |
| `--variant` als globaler CLI-Flag pro Invocation | Minimum-Complexity; für unterschiedliche Tags pro Modell separate Runs nötig | D-32 |
| Best-effort DB-Writes (try/except, log.warning) | Benchmark-Performance ist Primary Use Case; DB-Fehler dürfen Messung nicht stören | D-33 |
| systemd oneshot-Unit statt `/etc/rc.local` für CPU Governor | Standardisierte Lösung, `systemctl disable` zum Revert, keine rc-local-Abhängigkeit | D-34 |
| `num_ctx 512` für Benchmark-Varianten | Reduziert KV-Cache-Speicherbandbreite; für Voice-Assistant reichen 512 Tokens (kurze Prompts + kurze Antworten) | D-35 |
| LFM2.5-350M als Q8_0 (Ollama-Default) | Bei nur 379 MB kein Grund für stärkere Quantisierung; Q4_K_M wäre 229 MB (HuggingFace GGUF verfügbar) | D-36 |
| `num_thread=3` als optimaler Wert (nicht 4 oder 2) | Pi 5 hat 4 Cores — bei 4 Inference-Threads bleibt kein Core für Ollama-Server/OS frei, Thread-Contention halbiert Throughput | D-37 |
| `gemma3:1b-prod` als Produktionsmodell (num_thread=3, num_ctx=512, num_batch=128) | Kombination aller optimalen Parameter; num_ctx=512 reicht für Voice-Assistant (kurze Prompts + Antworten), spart KV-Cache-RAM | D-38 |
| LFM2.5-350M verworfen trotz schnellerem Cold-Start | Deutsche Sprachqualität unbrauchbar für Senioren-Zielgruppe (inkohärente Antworten, grammatische Fehler) | D-39 |

## 4 · Probleme & Lösungen

| Problem | Lösung / Workaround | Issue-ID (RAID) |
|---|---|---|
| Tuned-Modell-Benchmark fehlgeschlagen (404) | Falscher Modellname `gemma3-tuned` statt `gemma3:1b-tuned` (Ollama-Namenskonvention) | — |
| `sqlite3` CLI nicht auf Pi installiert | `sudo apt install sqlite3` — jetzt verfügbar für Ad-hoc-Queries | — |
| `OLLAMA_NUM_THREADS` Env-Var wirkungslos | Ollama ignoriert diese Variable (Log zeigt `NumThreads:4` trotz `OLLAMA_NUM_THREADS=2`). Lösung: `PARAMETER num_thread N` im Modelfile — wird korrekt übernommen | — |
| `echo -e "..." \| ollama create` schlägt fehl | `ollama create` akzeptiert kein stdin. Lösung: Modelfile als Datei schreiben + `-f` Flag verwenden | — |
