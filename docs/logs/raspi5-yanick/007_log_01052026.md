## 1 · Ziel dieses Schritts

Drei aufeinanderfolgende Features der MVP-Pipeline implementieren: (1) PIR-Sensor als physischen Trigger aktivieren, (2) Multi-Turn Conversation Memory innerhalb einer Session, (3) persistentes Long-Term Memory via SQLite, damit der Agent sich sessionübergreifend an Fakten über den Benutzer erinnert.

---

## 2 · Durchgeführte Aktivitäten

- **PIR-Sensor (HC-SR501) aktiviert**
  - Sensor physisch verdrahtet: Signal an GPIO4, 5V an PIN2, GND an PIN6
  - Kalibrationstool `test_pir.py` geschrieben und auf dem Pi getestet
  - Empfindlichkeit und Hold-Time über Hardware-Schrauben justiert (Sx/Tx)
  - `config.py` Default von GPIO17 auf GPIO4 geändert
  - Pipeline läuft nun standardmässig mit PIR-Trigger (`python main.py`)

- **Session Conversation Memory implementiert**
  - `chat()` in `llm_client.py` akzeptiert und returniert jetzt `history` (Liste von Message-Dicts)
  - `main.py` pflegt `history` über Loop-Iterationen hinweg
  - Timeout-basierter Reset nach 5 Minuten Inaktivität (konfigurierbar via `MEMORY_TIMEOUT`)
  - Verbaler Reset: Benutzer sagt "neue Frage", "neues Thema", "von vorne" oder "neues Gespräch" → History wird zurückgesetzt
  - Getestet: Agent erinnert sich korrekt an Namen innerhalb einer Session, vergisst nach Reset

- **Persistentes Long-Term Memory (SQLite) implementiert**
  - Neues Modul `memory.py`: SQLite-DB mit `user_facts` Tabelle (category/key/value Schema)
  - Nach Session-Ende (Timeout, verbaler Reset, Ctrl+C) extrahiert ein LLM-Call Fakten aus dem Gesprächsverlauf
  - Fakten werden als JSON-Array vom LLM zurückgegeben und in SQLite gespeichert
  - Beim Start der Pipeline werden gespeicherte Fakten geladen und in den System-Prompt injiziert
  - Upsert-Logik: gleiche Kategorie+Key → alter Wert wird deaktiviert (`active=0`), neuer eingefügt
  - `llm_client.py` refactored: `SYSTEM_PROMPT` → `_BASE_SYSTEM_PROMPT` + `build_system_prompt(facts_block)`
  - Getestet: Agent erinnert sich nach Neustart an Name und Katze des Benutzers

- **Robustheit verbessert**
  - Extraction-Timeout von 30s auf 60s erhöht (Kimi API manchmal langsam)
  - Retry-Logik: 2 Versuche mit 2s Pause
  - Fallback: bei Fehlschlag wird History als JSON in `pending_extractions/` gespeichert
  - Beim nächsten Start werden ausstehende Extraktionen automatisch nachgeholt (`retry_pending_extractions()`)

- **venv auf Pi mit `--system-site-packages` konfiguriert**
  - `lgpio` ist nur systemweit installiert (kein pip-Wheel auf arm64)
  - `python3 -m venv .venv --system-site-packages --upgrade` löst das Problem

## 3 · Technische Entscheide

| Entscheid | Begründung | Verknüpfung RAID |
|---|---|---|
| PIR auf GPIO4 statt GPIO17 | Physische Verdrahtung gemäss Datenblatt-Beispiel; config.py Default angepasst | D-10 |
| venv mit `--system-site-packages` | lgpio nur system-weit auf arm64 verfügbar, kein pip-Wheel kompilierbar (fehlendes `swig`) | D-11 |
| In-Memory Session History mit Timeout | Einfachste Lösung für Multi-Turn; 5 Min Timeout deckt typische Interaktionsdauer ab | D-12 |
| SQLite für Long-Term Memory | Stdlib (kein Dependency), schnell auf NVMe, Schema erweiterbar für Grafana/Logging | D-13 |
| Separate LLM-Funktion für Faktenextraktion | `chat()` verwaltet History und nutzt festen System-Prompt; Extraktion braucht eigenen Prompt ohne History-Management | D-14 |
| Async Extraktion in Daemon-Thread | Benutzer wartet nicht auf Faktenextraktion; bei Shutdown synchroner Call | D-15 |
